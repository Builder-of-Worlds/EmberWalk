# EmberWalk

Wildfire defensible space checks from one phone video, using Meta SAM 3.1 and Muse on Cloudflare.

The goal: the homeowner films one walk around the house, and EmberWalk finds what could carry fire to the house and ranks what to fix first, with the California rule behind each item. That full walk is not built yet; the status below says what is.

**Status, Friday Oct. 30th, 2026:** the building blocks below are written and tested locally, and a walk sent from the phone comes back as results in a test run on recorded model answers. Nothing is deployed, so no walk has gone from a phone through the live pipeline yet.

## Architecture

```
phone app ──upload in parts──> R2
    │                          │
    └──> API Worker ──starts──> pipeline (Workflows)
                                   ├─> media Container (ffmpeg: clip, audio, stills)
                                   ├─> SAM 3.1 (find each object in the walk)
                                   ├─> Muse Spark (judge each finding against the rule)
                                   └─> D1 (walks, findings, report)
```

| Phone app (React, offline capable) | `apps/web/` | Home, How it works, Record and Send screens behind hash routes (`src/router.ts`). The walk has two parts: the loop around the house, cut into front, sides and back at its compass corners, then a "Pan the Yard" pan of each side in the order the loop walked them; each part is sent as a tag labelled with its side, and every compass sample carries the light the camera saw; a walk with no compass, guided or one side reshot, sends the light readings on each tag instead, so the server judges each side's light without a heading (`src/parts.ts`, `src/light.ts`, `src/recorder.ts`, `src/sender.ts`). A service worker caches the app shell for offline use (`src/sw.ts`, `src/offline.ts`). A walk stopped by lost signal waits and sends itself when signal returns. While the server checks a sent walk, the phone shows its stages as a trail, with a bar only where the pipeline counts the steps finished in the stage now (`src/progress.ts`, `src/screens/Progress.tsx`). Results that name a side the walk could not check ask for that side only: `#/record/<walkId>/<side>` coaches one side, sends it as a part of the first walk (`partOf`), and opens the first walk's results once it is checked. A walk with something to fix lists first every open finding under 30 feet, nearest first by the server's measured distance from the house wall, whatever its label, and each row says how far it is (`fixFirstOf`, `src/results.ts`; `feetSaid`, `src/distance.ts`); when nothing open is under 30 feet, it lists the findings that block the green verdict, nearest first (`verdictOf`). Above the list, two lines count its rows inside 5 feet and from 5 to 30 feet. A walk with every side gapped asks for each side by name, never the whole walk. Results and finding screens open the bundled synthetic sample house (`src/samples.ts`, every sample checked as synthetic at load); the three newest results opened are kept on the phone (`src/results-store.ts`), and a sent walk's results are read from the API (`src/live-api.ts`). `npm run build:judge -w apps/web` builds a static copy of the sample houses into `apps/web/dist/judge/` that runs from any folder with no network calls; it is built and tested here only. | API Worker | `workers/api/` | Answers `GET /health` and the multipart upload API under `/api/uploads` (start, sign a part, complete, abort). Each part gets a SigV4 presigned PUT link straight to R2, with limits on part size and retries and a size cap set from the longest allowed walk (6 minutes). Only a walk in D1 that is waiting for its video can start an upload, with one open upload per walk, and completing it queues the walk and asks the pipeline to start it. `POST /api/walks` creates a walk that waits for its video (`workers/api/src/walk-create.ts`). `POST /api/walks/{walkId}/tags` stores up to 20 tags for a walk that is still waiting for its video, all or none (`workers/api/src/walk-tags.ts`). Three GET routes read a walk back for the visitor who made it, named by the `x-emberwalk-visitor` header (`workers/api/src/walk-read.ts`): `GET /api/walks/{walkId}` gives its state and any failure. Once the walk is done, `GET /api/walks/{walkId}/results` gives its open findings in rank order, each with its rule sources, proof frame, box and seconds into the walk, a preview link when a See It Fixed picture was made and the second check's verdict when it ran, plus the concepts that were not checked. `GET /api/walks/{walkId}/stills/{findingId}` streams that finding's own blurred still from R2 and nothing else, and `GET /api/walks/{walkId}/previews/{findingId}` streams its See It Fixed picture. `POST /api/faults` stores a fault report (a walk id, a refusal code and an app build) counted per walk, code and build, with a cap on new reports a day; it takes no visitor header (`workers/api/src/fault-report.ts`). The phone sends one report for each walk and refusal code when a status ask is refused in a way that holds the walk, and shows nothing about it (`apps/web/src/screens/Send.tsx`). The Get It Fixed routes (`workers/api/src/get-it-fixed-routes.ts`) check that the visitor owns the walk, job, message or finding, then pass to the Get It Fixed Worker: start with a ZIP, list jobs, draft, add a crew email, approve, mark a text sent, log a reply, follow ups and the inspection request. `POST /api/findings/{findingId}/status` saves a mark with its day, `GET /api/history` gives the dated record, and `/api/crew-optout/{token}` is the crew's opt out page. The Worker also serves the built phone app beside the API: `assets` in `wrangler.jsonc` points at `apps/web/dist`, `/api/*` and `/health` reach the Worker first, and any other path answers the app's `index.html`. Not deployed. |
| Walk pipeline (Workflows) | `workers/pipeline/` | A Workflow (`src/workflow.ts`) that claims a queued walk, probes the video and cuts a clip for the loop and the pan of the walk through the media Container (`src/prepare.ts`), uploads each clip to Meta and asks SAM 3.1 for each concept with retries (`src/segment.ts`), then stores the tracks and marks the walk done (`src/store.ts`). A refusal or a failure marks the walk failed with a plain reason. It also answers the API Worker's request to start a walk (`src/start.ts`). A coverage step after blur cuts two stills from the loop, and a third at the halfway point of any loop of 20 seconds or more with no usable compass; that halfway still is cut up front in the same container request as the two end stills, even when the halfway question is never asked, and that costs media time only, no model spend. It asks Muse Spark whether the walk's end meets its start; only when the end already looks like the start at 0.7 or more does it ask once more whether the halfway point differs from the start, so a guided walk can close from the video alone. It deletes the stills, stores the record at `coverage/<walkId>.json` and writes the side gaps to `walk_gaps` (`src/coverage-step.ts`). It calls Muse Voice Transcribe only when `VOICE_NOTES` is on (off in `wrangler.jsonc`). After the instructions are written, a second check asks Muse Spark Open on Baseten whether each kept finding's instruction fits its rule and stores the verdicts at `reports/<walkId>/second-check.json` (`src/second-check-step.ts`); it runs only when `BASETEN_API_KEY` is set, and on a real walk only when `SECOND_CHECK_REAL_WALKS` is `on`. A preview step asks Muse Image to show the top 3 findings fixed on their blurred stills and stores each at `previews/<walkId>/<findingId>.jpg` (`src/preview-step.ts`). Neither step ever fails a walk. Tested in the Workers test pool; not deployed. `wrangler.jsonc` binds the media Container as `MEDIA_CONTAINER` (class `MediaContainer`, `src/media-container.ts`, built from `containers/media/Dockerfile`) and `src/deps.ts` reaches it through that binding. No instance type is chosen yet, and `scripts/deploy.sh` refuses to deploy until one is set. No call has reached the Container under `wrangler dev` yet, because that needs Docker running. |
| Media Container | `containers/media/` | A Node server around ffmpeg and ffprobe: `POST /probe`, `/clip`, `/audio` and `/stills`, with limits on input size, length, height and frame count. The pipeline calls all four (`workers/pipeline/src/media.ts`): `/stills` for the coverage looks, the blur and pointing, and `/audio` only for voice notes. |
| Meta model client | `packages/meta/` | Calls SAM 3.1 on video, Muse Spark for text, JSON and tool calls, Muse Voice Transcribe on a WAV it checks before sending (mono, 16 bit, 16 or 24 kHz, at most 10 minutes and 32 MB), and Muse Image to edit a picture from a prompt (`src/image.ts`). A second transport reaches Muse Spark Open on Baseten, confirms the model is listed and retries timeouts (`src/baseten.ts`, `src/second-check.ts`). Prices every call, caches answers and refuses a call that would take the day's spend past a cap. The package keeps the cache and the spend ledger in memory; the pipeline plugs in a cache stored in R2 and D1 and the D1 ledger (`workers/pipeline/src/deps.ts`). SAM 3.1 and Muse Spark are called from the pipeline Worker today; Transcribe is called only by the voice notes steps, which are switched off (`VOICE_NOTES` in `workers/pipeline/wrangler.jsonc`). Tested offline, and in opt in live test runs against SAM 3.1 and Muse Spark (the first in commit 27d6fa1, $0.111). |
| Rules engine | `packages/rules/` | The California rule table (PRC 4291, Gov. Code 51182, 14 CCR 1299.03 and the CAL FIRE Zone 0 guidance) as data, each rule with its citation and zone distances. Looks rules up by what was seen, turns observations into findings ranked fix first, and checks recorded SAM answers and findings against a synthetic house's known answers. `coverageOf` turns a walk's compass samples, wall boxes, pan count and a same place look into side gaps, a loop verdict and a `CoverageRecord`. Pure functions, tested offline; the walk pipeline scores, explains and checks coverage with it, and the API Worker reads the rule table and coverage records through it. |
| Object catalog | `packages/catalog/` | Every object around a house that matters in a fire, as data in `src/catalog.ts`: the SAM text phrases, the Muse Spark pointing prompt where one is needed, why it matters, the cited source with the date read (or marked estimated), the bands it is checked in, and how it reaches the rules engine. An object whose concept is already in the shared `Concept` list names its rule key; house_wall and chimney map to their rule rows (the house wall is measured and never a finding; the chimney is a finding only for its spark arrester, and its branch rule fires only for a branch flagged near it); the ten new objects (gas can, stored fuel, lawn mower, grill, propane cylinder, vehicle, lumber pile, tarp, doormat, boat or trailer) are marked `pending: "shared"` with a proposed rule key, since a finding needs the shared enum and a rule row first. `checkCatalog` refuses a malformed row and runs once when the package loads. The pipeline asks SAM 3.1 for every object on the list (`rowsForClip`); the ten new objects are counted, not yet findings. |
| Explainer | `packages/explain/` | Pipeline step 5 as a module. Builds the one Muse Spark request per walk: the jurisdiction's rule table first, the same bytes for every walk so it can be billed at the cached rate, then the ranked findings, what the homeowner said and up to 10 proof frame links, asking for low reasoning effort and JSON by a schema; an answer that fails the schema is refused. The walk pipeline calls it as its explain step whenever a walk has findings, and stores the wording on each finding (`workers/pipeline/src/explain-step.ts`). |
| Get It Fixed agent | `packages/agent/` | The Muse Spark tool loop for one job (`src/loop.ts`): it offers two tools, `find_crews` and `draft_request` (`src/tools.ts`), checks every use against the job before it runs (the job's trade and ZIP, crews the job found, the job's own findings, one draft per crew, sample crews only on a synthetic walk), answers a failed check with an error the model can correct, asks again after a malformed turn at most twice, and stops at six requests. Both loops share one turn runner. `src/crews.ts` picks the job's nearest three crews before drafting, and `src/replies.ts` has Muse Spark read each saved crew reply into a price, a date, questions and a summary. Flagged off: it refuses unless told it is on; the Get It Fixed Worker calls it with the flag on. ## Stack

TypeScript, Cloudflare Workers, R2, D1 and Containers, React and Vite for the phone app (`apps/web/`), Cloudflare Workflows for the walk pipeline (`workers/pipeline/`), Zod, Vitest with the Workers test pool, ffmpeg, Blender with Python 3, Playwright.

## Setup

Needs Node 24, npm 11, Python 3 and ffmpeg (with ffprobe) on the path. Blender is optional.

```sh
npm install
```

## Tests

```sh
npm test
```

This runs every package's Vitest suite (Workers run in the local Workers runtime, D1 and R2 are local) and the Blender scene tests. The 11 scene re-measure tests and the 8 mask render tests need Blender, and one probe test needs ffmpeg; each is skipped when its program is missing. No test calls a paid model.

Also: `npm run typecheck`, `npm run lint`, `sh tools/license-check.sh` (every installed package must carry a permissive license), and the browser tests of the site and the phone app with `npm run test:e2e -w workers/static` and `npm run test:e2e -w apps/web` (they need a Chromium for Playwright).

## The story

Defensible space is the buffer a homeowner keeps between a house and the plants, wood and clutter that could carry fire to it. Checking it by hand means walking every side of the house with a checklist. EmberWalk aims to turn that walk into one phone video: film once, get a ranked list of what to fix, each item with the rule behind it and the picture that shows it.
